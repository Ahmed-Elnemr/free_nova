## 1. Core Domain Concepts

### 1.1 Identity & Code Generation
- Every user who completes a compatibility profile receives a unique **Personal Code** auto-generated by the system.
- Format: 4 random distinct digits + 2 characters indicating gender (`M` for male, `F` for female). Example: `1234ML`.
- The personal code is immutable once generated.
- Age is always computed automatically from date of birth to current date and displayed in years only — never stored as a raw age input.

### 1.2 Gender Lock
- Gender (male/female) is selected once during registration and can **never be changed**.
- The system must warn the user of this irreversibility at the point of selection before allowing them to proceed.

### 1.3 Ethnicity Lock
- Ethnicity (White/Brown) is selected once during profile completion and can **never be changed**.
- The system must warn the user of this irreversibility at the point of selection before allowing them to proceed.

### 1.4 Guardian Data (Wali Al-Amr)
- Required only for female users, both at registration and profile editing.
- Fields: guardian full name, guardian mobile number, relationship.
- All three fields are mandatory for female accounts.
- Changes to guardian data are recorded and trigger an admin notification.

## 2. User Types & Roles

| Role | Context | Key Capability |
|---|---|---|
| Visitor | Mobile App | Can open app, browse splash screens, see main screen shell — cannot access any functional feature |
| Registered User (Male) | Mobile App | Full app access; can send one connection request at a time |
| Registered User (Female) | Mobile App | Full app access; cannot send connection requests — receives them passively |
| System Admin (Super) | Admin Panel | All permissions; creates other admins |
| System Admin (Sub) | Admin Panel | Permissions defined by super admin at creation |

### 2.1 Visitor Logic
- Visitor mode exists solely to satisfy app store (Apple) review requirements.
- Any interaction requiring account data (notifications, connection requests, more menu actions) must trigger a login prompt popup instead of performing the action.
- After app store approval, the visitor button may be hidden — but the underlying route remains valid.
- A visitor who is already logged in bypasses onboarding and lands directly on the main screen.

## 3. Authentication & Account Lifecycle

### 3.1 Registration — Common Rules (Both Genders)
- **Mobile number:** exactly 10 digits, must start with `05`, Saudi format only.
- **Full name:** string, minimum 3 characters, maximum 100 characters.
- **Date of birth:** date picker, cannot be a future date, mandatory.
- **National ID:** digits only, exactly 10 digits, must start with `1` or `2`.
- **Terms & conditions checkbox:** must be checked — proceeding is blocked until checked.
- Mobile number must be unique in the system (not already registered).
- After submitting the form, an OTP is sent to the provided mobile number.
- OTP is **6 digits** for female registration, **4 digits** for male registration.
- OTP has a validity window; resend is available after the timeout expires.
- After successful OTP confirmation, the account is created and the user is automatically logged in and redirected to the main screen.

### 3.2 Registration — Female-Specific Additional Fields
- Guardian name: string, 3–100 characters, mandatory.
- Guardian mobile: 10 digits, starts with `05`, Saudi format, mandatory.
- Guardian relationship: string, 3–100 characters, mandatory.

### 3.3 Login
- Input: mobile number only (10 digits, starts with `05`).
- System checks if the number is registered and active.
- If registered: send OTP → user enters OTP → login succeeds → redirect to main screen.
- If not registered: show error "Number not registered, you can create an account."
- If OTP is wrong or expired: show error with resend option.
- Empty mobile field: block submission, show validation message.
- OTP resend window: 60 seconds.

### 3.4 Session & Onboarding
- Onboarding (splash screens) is shown only on first launch or after logout.
- If the user is already logged in, skip onboarding and go directly to main screen.
- Language selected during onboarding persists throughout the session until manually changed.
- Supported languages: Arabic, English.

### 3.5 Account Deletion
- User initiates account deletion from the "More" menu.
- System shows confirmation dialog: "Are you sure you want to permanently delete your account?"
  - **Cancel:** no action, stay on current screen.
  - **Confirm:**
    - If the user has any **active (non-completed, non-rejected) connection requests**, deletion is **blocked**. Show error: "Cannot delete account due to pending connection request."
    - If no active requests: account is deleted; all associated connection requests remain visible in the admin panel for records.
    - An admin notification is sent identifying the user who deleted their account.
    - The same mobile number / national ID may be re-registered; any new connection requests are linked to the new account.

### 3.6 Logout
- Confirmation popup: "Are you sure you want to logout?"
  - **Cancel:** stay in app.
  - **Confirm:** session is fully terminated, redirect to login screen.
- After logout, onboarding is shown again on next app launch.

### 3.7 Phone Number Change
- User enters new mobile number meeting all standard mobile validation rules.
- System sends OTP to the new number.
- Change is applied only after correct OTP entry.
- New number must not already exist in the system for another account.
- If the new number is already linked to another account: show error "Number linked to another account."

### 3.8 Admin Password Recovery
- Admin enters registered email address.
- System sends OTP to that email.
- After correct OTP, admin sets a new password.
- Password requirements: minimum 8 characters, must include uppercase, lowercase, and digits.
- Expired or wrong OTP: show error with resend option.
- Email not found: show error "Email not registered."
- After successful reset, redirect to login screen.

## 4. Compatibility Profile (Tawafuq File)

### 4.1 When Profile is Required
- On first login, if no compatibility profile exists, the main screen shows a prominent "Complete Compatibility Profile" button.
- The user must complete this profile before any matching results are shown.
- While the matching search is still running after profile completion, the main screen shows a "Search in Progress" state.

### 4.2 Profile Fields & Validation

| Field | Type | Rules |
|---|---|---|
| Personal Code | Auto-generated | Read-only; shown on profile |
| Gender | Auto-filled | From registration; read-only |
| Age | Auto-computed | From date of birth; displayed in years only |
| First/Alias Name | String | 3–100 chars, mandatory |
| Age Range for Other Party | Two numeric fields | Integers only, max 2 digits (e.g. 99), both mandatory |
| City | Dropdown | From admin-managed active cities list, single select, mandatory |
| Marital Status | Dropdown | Values: Single, Married, Divorced — single select, mandatory |
| Educational Qualification | Dropdown | From admin-managed active qualifications list, single select, mandatory |
| Occupation | String | 3–100 chars, mandatory |
| Religious Commitment | Dropdown | Values: Sunni, Shia — single select, mandatory |
| Ethnicity | Dropdown | Values: White, Brown — single select, mandatory; irreversible warning shown |
| Tribe/Family | String | 3–100 chars, mandatory |
| Bio | String | Up to 1000 chars, optional |
| Compatibility Questions | Yes/No per question | Admin-defined questions; one answer per question, mandatory |

### 4.3 Profile Save & Update
- On save, the compatibility search immediately re-runs based on the updated data.
- User is redirected to the main screen.
- Profile can be edited at any time from the "More" menu → Compatibility Profile.
- Every save triggers an immediate re-computation of all compatibility scores against the opposite gender.

### 4.4 Profile Visibility Rules
- Male profile data (code, gender, age, ethnicity, first name, other-party age range, city, marital status, qualification, occupation, religious commitment, tribe/family, bio, required specifications) is shown to females when they open a connection request or view a match card.
- Female profiles are **never** shown to males. Males only see female match cards (with code, age, marital status, city, qualification, compatibility %).
- Male data becomes visible to the female only when a connection request's status changes to "Guardian Contacted."

## 5. Compatibility Matching Engine

### 5.1 Matching Criteria
Compatibility score is calculated by comparing:
- Ethnicity match
- Religious commitment match
- Age range compatibility (does the other party's age fall within the specified range)
- Marital status match
- All admin-defined Yes/No specification questions (compared pairwise)

### 5.2 Score Threshold
- Only profiles with **50% compatibility or higher** are shown to a user.
- Results are displayed from highest compatibility to lowest (descending order).
- If no profiles meet the 50% threshold: show empty state with message "No compatible profiles found. You will be notified when a match appears."

### 5.3 Filtering on Main Screen
Filters are available on the main screen and apply on top of the 50% threshold:
- **Age range (from–to):** numeric, integers only, max 2 digits each.
- **City:** dropdown of active cities.
- **Marital status:** dropdown (Single, Married, Divorced).
- **Educational qualification:** dropdown of active qualifications.
- Multiple filters may be applied simultaneously.
- "Clear Filters" button resets all filters and shows the full matched results.
- All filtered results remain sorted highest to lowest compatibility.

### 5.4 Match Card Data
Each card in the main screen list shows:
- Compatibility percentage
- Personal code
- Age (computed, years only)
- Marital status
- City
- Educational qualification
- "Send Connection Request" button (for males) or the equivalent for females

### 5.5 Full Profile View
- Clicking a male profile card opens his full data (all fields listed in 4.2).
- If a connection request for this male is currently in "Accepted" status, the female sees an empty state page with the project logo background and message: "You have an accepted request. Content will be updated based on request status change."
- If a request for this male is in "Completed" status, the female sees a "Complete Compatibility Profile" button directing her to update/reconfirm her profile.

## 6. Connection Request Workflow

### 6.1 Sending a Request
- Only males can initiate a connection request.
- Before sending, a confirmation popup appears: "Are you sure you want to send a connection request?"
  - **Confirm:** request is sent to admin panel with status "New."
  - **Cancel:** return to main screen.
- A male can have only **one active connection request at a time** (i.e., not in a terminal state). He must wait for the admin's response before sending another.

### 6.2 Request Status Lifecycle

```
New → Under Review → Guardian Contacted → Accepted → Completed
                ↓                    ↓             ↓
             Rejected            Rejected       Rejected
```

- **New:** Created when male sends request. Admin has not yet reviewed it.
- **Under Review:** Admin manually moves it from New. Both parties are notified.
- **Guardian Contacted:** Admin has contacted the female's guardian (external action). Admin moves it from Under Review. Both parties are notified. Male's full data becomes visible to the female from this point.
- **Accepted:** Admin moves from Guardian Contacted. Both parties are notified. All other pending requests for the same female are automatically set to **Temporarily Suspended**.
- **Temporarily Suspended:** Applies to other requests when one is Accepted. The suspended request's other party sees a notice "The other party currently has an accepted request."
- **Completed:** Admin moves from Accepted. Both parties are notified. "Accepted" status is no longer reversible; it can only progress to Completed. The Report button becomes available only when a request is in Accepted status.
- **Rejected:** Admin can reject from any status **except Completed**. Both parties are notified. When rejected, other suspended requests are un-suspended.

### 6.3 Report Button Availability
- The report (Balaghaat) submission button on a connection request card is **only visible when the request status is Accepted**.
- It is hidden for all other statuses.

### 6.4 Notifications on Status Change
Every status transition triggers push notifications to both the male and female user involved.

### 6.5 Connection Request Display (User Side)
Tabs: All | New | Under Review | Guardian Contacted | Accepted | Temporarily Suspended | Completed | Rejected.

Card data shown:
- Request number (auto-generated unique)
- Compatibility percentage
- Personal code
- Age
- City
- Marital status
- Educational qualification
- Request status

For female users: additional "View More" button on each card to see full male profile data.

Admin can send push notifications to:

- Females only

Fields: notification title, notification body.

## 10. Admin Panel — User Management

### 10.1 Search Filters
- User name
- Mobile number
- National ID
- Status (Active / Disabled)

### 10.2 User Detail View
**Male:** full name, mobile, date of birth, national ID + full compatibility profile fields.
**Female:** full name, mobile, date of birth, national ID + guardian data (name, mobile, relationship) + full compatibility profile fields.

### 10.3 Disable User
- Requires entering a reason (mandatory).
- Effect: user's status becomes Disabled; active session is terminated; user cannot log in; on next login attempt, user sees the disable reason.
- An email is sent to the user citing the reason.
- Cannot disable a user who has **active bookings / ongoing requests** (non-completed, non-rejected).

### 10.4 Enable User
- User's status returns to Active; user can log in again.
- An email is sent to the user confirming reactivation.

### 10.5 Export
- Results can be exported as PDF and as Excel.
- Export includes all user data fields visible in the management table.

### 10.6 Acceptance Criteria
- Search works by name, mobile, national ID, or status.
- Disable/Enable buttons appear only for the correct status (Disable for active, Enable for disabled).
- Reason is mandatory before disabling.
- Email sent on both enable and disable.
- Active session is terminated immediately on disable.
- Previous data is preserved after disable or enable.

- Status changes apply in real-time across the entire system (admin panel + mobile app).

### 12.3 Acceptance Criteria

- Search by question text or status.
- Total question count displayed at top of management page.

## 23. Cross-Cutting Rules

### 23.1 Data Integrity
- Deleting or deactivating any reference data (city, qualification) is blocked if any active record depends on it.
- Deleting a user account does not delete their historical connection request records.

### 23.2 Real-Time Updates
- Connection request status changes must propagate in real-time to all parties (both app users and admin panel).
- Notification delivery must be real-time.
- Dashboard stats refresh in real-time or near-real-time.
- Report arrivals in admin panel are real-time.

### 23.3 Empty States
All list screens must show a meaningful empty state message when no records exist or no search results are found. Generic empty-state messages are unacceptable — they must contextually describe what is missing.

### 23.4 Field-Level Validation
- Every mandatory field that is left empty shows a field-level error message: "This field is required."
- Submission of any form is blocked while any mandatory field is invalid or empty.
- Character limit enforcement: user cannot type beyond the maximum allowed characters for any field.
- Character minimum enforcement: field-level error shown if below the minimum on form submission.

### 23.5 Error & Success Feedback
- Every action (save, send, delete, status change) must return a clear success or failure message.
- Error messages must identify the specific reason for the failure.

### 23.6 Confirmation Dialogs
The following actions always require a confirmation dialog before execution:
- Sending a connection request
- Deleting an account
- Logging out
- Disabling a user or admin
- Deleting any record (city, qualification, role, admin, etc.)

### 23.7 Pagination & Counting
- All management tables in the admin panel display a total count of records at the top of the page (below the section title).
- Pagination or infinite scroll applies to all lists with potentially large record sets.

### 23.8 Export Consistency
- Exported files (PDF / Excel) must reflect the currently filtered/searched result set, not the full unfiltered dataset — unless no filter is active.

### 23.9 Permission Enforcement
- Every admin panel page and action is gated by the permission assigned to the logged-in admin's role.
- Attempting to access a page without the required permission results in an access-denied response.
- Super admin always retains all permissions regardless of role configuration.

### 23.10 Session Security
- On account disable (user or admin), the active session is terminated immediately.
- On password or email change for an admin, the active session is terminated immediately and the admin must log in again with new credentials.

### 23.11 Notification Linking
- Every notification that relates to a specific screen (e.g., connection request update, report reply) must navigate the user to that screen when tapped.
- Notifications that are purely informational (e.g., welcome, admin broadcast) do not need to navigate anywhere.
